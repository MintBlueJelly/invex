# InvEx — code review

A test-driven review of the whole pipeline, ranked by what it costs **this** deployment
([DEPLOYMENT.md](./DEPLOYMENT.md)) rather than by code aesthetics.

Every claim here is backed by a test that runs. Nothing below is an opinion about how the code reads;
each finding was reproduced by executing the path, and each has an `INVEX-nnn` id in
[docs/known-bugs.md](./docs/known-bugs.md) with the test that pins it. Where the original review notes
turned out to overstate a problem, the entry says so.

**State:** 53 findings — **11 fixed** with regression tests, **42 pinned** as a machine-checked
backlog. The suite went from 71 tests to 799 across six lanes; coverage from 89.0 % to 96.3 % lines
and 70.8 % to 83.9 % branches. CI now runs it and gates the image build.

## The finding that shaped everything else

**The test suite could not fail for the right reason.** `out/expected.json` was regenerated by the same
`computeInvoice()` that rendered the fixture PDFs, so the suite compared the pipeline against its own
arithmetic. And because `computeInvoice()` filled `quantity`, `unitPrice` and `taxRate` on every line,
**no fixture ever gave the solver something to reconstruct** — the solver's entire stated purpose
(briefing §1/§4) was untested.

That is not an abstract concern. `INVEX-034` is the concrete cost: a parenthesised qualifier after a
label defeats value extraction, and `packages/fixtures/src/textPdf.ts` printed exactly
`"Zwischensumme (netto)"`. So the canonical text fixture never extracted `totals.net` by rule;
`R_NET_FROM_LINES` repaired it instead — and `API.md`'s worked example records that repair as the
expected path. **A defect became the documented behaviour, because the fixture and the expectation
shared an author.**

Verified directly:

```
"Zwischensumme (netto) 1.148,70"  →  totals.net = undefined
"Zwischensumme 1.148,70"          →  totals.net = "1148.70"
```

The oracle was rebuilt (see [The test suite](#the-test-suite)) and found two more defects on its first
run.

**A second observation worth internalising:** coverage was already **89 % lines / 90 % functions** while
all of this was true. The integration tests *executed* nearly the whole pipeline and *asserted* very
little about it. Coverage was never the missing thing.

## Fixed

Eleven defects, one commit each, every one demonstrably red before the change and green after.

### Silent financial corruption

These produced schema-valid, self-consistent, fully-reconciled invoices that were simply wrong. Nothing
in the pipeline could detect them and nothing escalated.

**`INVEX-001` — template locale induction multiplied a vendor's amounts by 100, permanently.**
`amountVariants()` listed the canonical dot-decimal form in *both* locale candidate sets, so
`detectLocale` could never return `"."`. An ungrouped English page was induced as `decimal: ","`, and
the persisted template then read `1148.70` as `114870` — for that vendor, on every future invoice, with
full `template` provenance.

The exploratory notes claimed this was always silent. It is not, and the distinction matters: scaling
preserves `net + tax = gross`, so the outcome depends on whether the VAT *rounding residue* survives.
`1148.70 × 19 %` leaves `0.003`, which scales to `0.3` and trips C4's absolute ±0.02 tolerance — but
`1000.00 × 19 % = 190.00` exactly, and that invoice reconciles with **zero violations**. Round net
amounts are common, so it is silent often enough to matter. Both cases are now pinned as tests.

**`INVEX-002` — OCR column bleed shifted whole rows.** Bands were assigned by a token's left edge with a
flat 0.02 tolerance; amount columns are right-aligned, so a value wider than its header starts to the
*left* of it. The consequence was worse than reported: not a lost cell but the entire row moving one
column across — `quantity` became `"2199.50"` (fused with the unit price) and `unitPrice` silently held
the line total. Every value stayed schema-valid.

**`INVEX-003` — `parseAmount` fused two merged cells into one plausible number.** `"199,50 399,00"` →
`19950399.00`. Now declines; a null is a missing field the solver reports, a fused number is a wrong
invoice nobody sees. Space-grouped amounts (`"1 234 567,89"`) still parse.

**`INVEX-004` — review commit bypassed the solver and then poisoned a vendor template.**
`PUT /api/review/:id` validated shape only, never re-ran the constraint system, and induced a template
from the unchecked numbers. The one place a human's mistake is *amplified* rather than contained.
Now returns `422` with the failing constraints; the document stays in `pending_review` and no template
is induced. `C5_VAT_CLOSED_SET` deliberately does not block — a reviewer looking at an Austrian 20 %
invoice is the authority. They may assert an unusual rate; they may not assert that the totals
contradict each other.

**`INVEX-005` — a missing docling page size collapsed every bbox to `[1,1,1,1]`.** Region anchors, the
classifier's heading-position feature, the segmenter and the OCR x-bands all then ran on degenerate
geometry, silently. Now falls back to A4 — but only when the observed coordinates actually fit it; an
A3 page or a schema change throws instead of producing plausible nonsense.

### Operationally dangerous at one replica

**`INVEX-006` — the rasterizer had no dimension guard.** A 200×200 inch MediaBox at 150 dpi asks for
~900 megapixels (~3.6 GB) against a 1Gi limit. The OOM rolls the claim transaction back **without
incrementing `attempts`**, and claims are oldest-first, so the document is re-claimed on every restart
and blocks everything behind it. This is `DEPLOYMENT.md`'s poison document, and the intended entry point
is email attachments. Now rejected before allocating, which turns a wedge into an ordinary stage error.

**`INVEX-007` — three retries burned in one event-loop burst.** A stage error returned "processed",
skipping the poll sleep, so the next tick re-claimed the same row immediately. The interleaved trace was
literally `attempt, attempt, attempt`. One docling restart, or one llama-swap 503 during a cold model
load — both routine — drove every in-flight document to `failed`, a status with no handler and no
requeue endpoint.

**`INVEX-008` — five endpoints returned 500 with the failed SQL and its bound parameters in the body.**
Unvalidated `:id` reached a uuid column. Wrong status code and internals disclosure on the same request.

**`INVEX-009` — `/health` could not report unhealthy.** Always HTTP 200, so a Kubernetes probe could
never fail, and it said nothing about the worker. `DEPLOYMENT.md` lists this first in its troubleshooting
table and calls it structurally undetectable. Now 503 when degraded, with worker liveness — and
deliberately *not* degraded by docling being down (it recovers on its own) or by a tick legitimately
sitting inside a 300 s VLM call.

### Correctness

**`INVEX-010` — every §19 Kleinunternehmer and §13b reverse-charge invoice escalated.** A `rate > 0`
guard meant a `{rate: 0, tax: "0.00", net: null}` entry — exactly what `runRuleEngine` emits — could
never be completed. Now apportioned from the header, which is also more accurate for *any* rate: the
printed tax is already rounded, so back-computing `218.25 × 100/19` yields `1148.68` for an invoice whose
header states `1148.70`. **That second half was found by the golden corpus, not by inspection.**

**`INVEX-011` — three defects in the store the entire feedback loop depends on.** `version` computed in
JS (lost update); `listTemplates` sorted *ascending*, returning the 100 oldest templates and never the
ones just learned; and — worse than reported — a non-matching USt-IdNr did not stop IBAN resolution, so
two vendors sharing a payment-provider IBAN **collapsed into one row** and the second overwrote the
first's checksum-verified identity.

## Still open, ranked

42 findings, all pinned. Deliberately not fixed: each changes what the extractor *outputs*, and the right
output is a question the golden corpus and real documents should answer, not one to guess at. Full detail
in [docs/known-bugs.md](./docs/known-bugs.md).

### 1 — Deterministic coverage is being thrown away

This group costs money on every document, because work that should stay on the CPU goes to the GPU.
It is the design centre of the whole system (briefing §1) and the most valuable thing to fix.

**`INVEX-047` — the text gate rejects legible invoices.** Two compounding causes: `runTextGate` reads
`doc.lines` only, so it **judges the text layer while never seeing `doc.tables`** — where most of an
invoice's words are — and `minDictHitRate: 0.55` is far too high for what remains (letterhead, labels,
amounts, proper nouns). Three of eight golden scenarios, including a plain German business letter, score
0.47–0.55 and are rerouted to OCR. For an unknown vendor that means the GPU. The old suite had one text
fixture; it scores 0.65.

**`INVEX-034` — a parenthesised label qualifier defeats extraction**, described above. `"Zwischensumme
(netto)"` is an ordinary German subtotal label.

**`INVEX-017` / `INVEX-018` — the rule engine's heuristics contradict each other.** "Last amount on the
line" turns `"Nettobetrag 1.148,70 zzgl. 19% MwSt"` into a net of **19**; the source comment justifies
last-match with `"MwSt. 19%: 218,25"`, which is the opposite ordering — one heuristic cannot serve both.
And `"Satz"` is a `unitPrice` synonym matched by substring, so `"Steuersatz"` is claimed as the unit-price
column; which key wins depends purely on left-to-right column order. There are 10 such cross-column
collisions in the shipped lexicon.

**`INVEX-036` / `INVEX-038` — vendor identity is lost, or invented.** The IBAN scan regex is
case-sensitive, so lowercase OCR output yields no IBANs at all — on the lane where OCR noise is expected.
And the DE VAT-id scan uses `[\d\s]`, which includes newlines, against newline-joined text: a `DE` ending
one line **absorbs digits from the next into a fabricated VAT id**. Demonstrated producing one that passes
the ISO 7064 checksum by coincidence.

**`INVEX-042` — `findField` slices the value from the wrong place** when a line carries its label twice;
demonstrated returning a *superseded* invoice number over the current one.

### 2 — Path A silently degrades

**`INVEX-024`** — repeated CII elements become arrays and the helpers return null for arrays. ZUGfERD
EXTENDED legitimately emits one `TaxTotalAmount` per currency, so a **declared** tax total silently
becomes null and the solver re-derives it. Same blindness loses every IBAN when several payment-means
blocks are present. **`INVEX-025`** — a line whose description sits only in `SpecifiedTradeProduct/
Description` is dropped entirely, breaking the line-sum constraint with no indication why.
**`INVEX-023`** — `fieldMeta` is keyed on the source index while lines are pushed at the destination
index, so one skipped item desynchronises provenance for everything after it.

### 3 — Configuration that fails quietly

**`INVEX-053`** — `VLM_ENABLED=1`, `=yes`, `=TRUE` or `=on` all silently **disable** the VLM. Your cluster
switches the entire escalation path on with that one variable. **`INVEX-020`** — an unknown or misspelled
classifier weight key contributes 0 with no error, for a value the briefing says must be empirically
calibrated. **`INVEX-054`** — `PORT=web` binds an arbitrary free port instead of failing.

### 4 — The untrusted-input surface

The trust model changes the moment n8n is wired: `DEPLOYMENT.md` justifies having no authentication by
keeping InvEx on a trusted network, but the *intended* entry point is IMAP attachments — arbitrary bytes
from the internet.

**`INVEX-055`** — ingest accepts any bytes as a PDF (no magic number, no media type, field name unchecked)
while allowing 50 × 100 MB per request into the Node heap and then into Postgres, the database
`DEPLOYMENT.md` identifies as the only copy of every document. **`INVEX-057`** — a NUL byte in a filename
reaches Postgres and returns 500 with the SQL and its bound parameters; attachment filenames are
attacker-controlled text. **`INVEX-056`** — ingest is not atomic across parts, so a later failure orphans
the already-committed documents with no id returned to the caller.

The good news: the adversarial corpus (Phase 7′) confirms the **queue survives all of it** — ingest every
malformed input in the corpus and a known-good invoice still commits afterwards.

### 5 — The clients that talk to the cluster

**`INVEX-048`** — the VLM client retries *only* on unparseable JSON, so a 503 while llama-swap swaps
models — routine, with cold loads measured at 1 m 29 s to 2 m 38 s — costs the document an attempt rather
than being retried. **`INVEX-051`** — the docling client has no retries and no response validation; a
proxy's HTML error page with status 200 surfaces as a bare `SyntaxError`. **`INVEX-049`/`INVEX-050`** — a
token-truncated response is reported as "non-JSON output" (capacity problem indistinguishable from a bad
model), and fence stripping handles only one leading and one trailing fence, so a `<think>` block from a
reasoning model defeats it.

## Improvement potential, given this deployment

Ranked by what the deployment's own constraints make expensive.

**1. Widen the deterministic path — the highest-value work available.**
`INVEX-047`, `INVEX-034`, `INVEX-017`, `INVEX-018` and `INVEX-036` all push documents that should have
been handled on the CPU toward OCR, the VLM, or human review. With one GPU shared between Open WebUI,
docling's captioning and InvEx's escalations, and a cold big-model load costing 1½–2½ minutes against a
300 s client timeout, each avoidable escalation is expensive in a way no profiler will show you. These are
also the *cheapest* fixes in the list — heuristics and one threshold.

**2. Stop holding a database connection across a 300-second network call.**
`claimNext` opens a transaction and holds `FOR UPDATE` on the row for the entire stage — including
`docling.convert` and `vlm.extractStructured` — on a pool of 10 shared with the HTTP API. A handful of
slow documents pin connections `idle in transaction` for minutes, block autovacuum, and starve the API.
Committing the claim before the network call and re-acquiring afterwards would remove the coupling
entirely. *(Not pinned: it needs the real-Postgres lane to demonstrate.)*

**3. One replica processes strictly serially.**
`tick()` handles exactly one document and the loop awaits it, so `SKIP LOCKED` buys nothing at one pod
and the 10-connection pool is unused. A small intra-process concurrency knob would multiply throughput
without touching the deployment topology — and the claim logic is already correct for it.

**4. Dead and misleading configuration.**
`config/prompts/classify.md` is **never loaded** — `vlmEscalate.ts` unconditionally reads
`invoice-extract.md`, yet the response schema demands `isInvoice` and `markdown`, which that prompt never
mentions. A non-invoice sent to the VLM gets an extraction-only instruction. `templates.minFieldConfidence`
is validated and read by no code, reading like an implemented quality gate that does not exist. And
`vlm.requestTimeoutMs` also governs the **docling** client, so `DEPLOYMENT.md`'s timeout ladder understates
what that knob controls.

**5. The classifier's `uncertain` band is inert as shipped.**
With `vlm.enabled: false`, scores 4–6 have no consumer — `textLane.ts` gates on it — so the briefing's
three-band design collapses to two, and no document tells you. Your cluster sets `VLM_ENABLED=true`, so
this bites the repository default rather than production; but see `INVEX-053`, where a plausible spelling
of that variable silently turns it back off.

**6. `pending_review` is a black hole in production today.**
Not a code defect — an operational gap. There is no review UI (a deliberate MVP cut) and n8n is not wired,
so escalated documents land in a status nobody observes. The briefing's feedback loop — every escalation
creates or updates a template — is the system's entire reason for existing, and it is currently open at
the human end. `GET /api/review` is the whole interface.

## The test suite

Six lanes, split by what a test owns and the cheapest thing that can hold it. `pnpm test:unit` is the
inner loop at ~1.5 s.

| lane | tests | what it owns |
| --- | --- | --- |
| `unit` | 638 | one exported function's contract; no I/O |
| `prop` | 11 | fast-check invariants |
| `component` | 79 | one repo / stage / route group over PGlite |
| `integration` | 67 | stage composition, status trajectories, event traces |
| `e2e` | 4 | the CLI contract against a real listening server |
| `pg` | — | declared, empty: needs real Postgres (deferred) |

**The oracle.** Each golden scenario carries two independently authored halves — `render.doc`, exactly the
ink on the page as literal strings, and `expected.canonical`, the invoice a competent human reading that
page would type. Neither is computed. One layout seam renders every representation (text PDF, scanned PDF,
Docling JSON, OCR JSON), so the PDF and the Docling JSON can no longer describe different pages — the drift
the hand-written `doclingFixtures.ts` was always free to introduce. That file is deleted; the ratchet
forbidding new `computeInvoice` imports is empty and stays in place.

Two guards keep a hand-authored oracle honest: `goldenConsistency` re-derives every scenario's arithmetic
from ~15 lines of `Decimal` shared with nothing and checks that every printed amount appears in the
expectation; `goldenPurity` blocks any new file reaching for the old generator.

**Known-bug pins use `it.fails()`**, not a skipped lane. The decisive property is what happens when the bug
is *fixed*: a skipped test tells nobody and lets the fix ship without its regression test. These go **red**
the moment the defect is repaired. Every pin is paired with a green `[current]` test recording today's
behaviour, and all 62 were verified to turn red under `INVEX_KNOWN_BUGS=strict` — a pin that passes both
ways asserts nothing.

**The loop that carries this forward.** `pnpm fixtures:label <pdf>` turns a real invoice you triage into a
draft scenario from the pipeline's own output, marked `reviewed: false`. A draft may not be used as an
expectation until a human corrects it — enforced — because a draft used as an oracle asserts only that the
pipeline agrees with itself. `pnpm smoke --strict-canonical` then compares field by field with dotted
paths; previously the harness checked the gross total and the line *count* and nothing else.

Label enough real documents this way and briefing §11's open item closes itself: the classifier band
calibration finally has its sample.

## What I did not do

- **The concurrency lane is declared and empty.** PGlite is single-connection, so `FOR UPDATE SKIP LOCKED`,
  the `upsertTemplate` lost update and the ingest dedup race are structurally untestable there. An agent
  tried 25 concurrent identical ingests ten times and could not reproduce the race — and said so rather
  than writing a test that passes for the wrong reason. These need real Postgres. The `pg` project exists
  so the lane slots in without reconfiguring.
- **`INVEX-006`'s red state was never demonstrated by execution.** Proving the absence of the guard means
  attempting a ~3.6 GB allocation. The boundary tests prove the guard works; I did not prove the crash.
- **The docling mapper is still not pinned against a live response.** It is now tested against a rendered
  fixture from the shared layout seam rather than hand-typed JSON, which removes the drift risk — but
  `docker-compose.yaml` still pins v1.26.0 while the cluster runs v1.27.0, and neither has been captured.
  This remains the open item `README.md` already flags.
- **Nothing is pushed.** 21 commits sit on `main` locally. `README.md`, `API.md` and `DEPLOYMENT.md` were
  already uncommitted when I started; `API.md` carries my edit documenting the new `422` but is otherwise
  untouched and unstaged.

## Where I would start

1. **`INVEX-047`** — one threshold and one input change, and it stops sending legible invoices to the GPU.
2. **`INVEX-053`** — a one-line fix on the variable that switches your entire escalation path.
3. **`INVEX-034`, `INVEX-017`, `INVEX-018`** — the rule-engine heuristics, which widen the deterministic
   path further and are pinned with tests that go green the moment they are right.
4. **Then feed it real invoices** and label them. Every finding above was inferred from synthetic
   documents and the deployment description; the corpus becomes worth far more when it stops being a guess
   about German invoices and becomes a record of yours.
